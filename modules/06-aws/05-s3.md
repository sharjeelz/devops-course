# S3

> **You need:** Lesson 4 (Linkly running on the instance) · **Time:** ~60 min · **Cost:** cents (S3 storage and requests for a few small files) · **Start from:** `checkpoint/06-aws`

## Why this matters

Linkly's links live only on the instance's disk. Lose the instance and they're gone. S3 is
where backups, logs, static files and Terraform's state (Module 7) go: cheap, durable storage. And
the server should be able to write there **without any password stored on it**.

## Concept

- **Buckets and objects:** a bucket holds objects (files) under keys (names). Bucket names are
  global across all of AWS, so add something unique (`linkly-course-<random>`).
- **Private by default:** **Block Public Access** stops anyone from making the bucket or its
  objects public by mistake. Leave it on unless you're deliberately hosting public files.
- **Versioning:** keeps every version of every object, so an overwrite or delete can be undone.
- **Encryption at rest** is on by default for new objects (SSE-S3).
- **Lifecycle rules** move or expire old objects automatically (e.g. delete backups after 30 days).
- **Instance role:** a **role** (`linkly-course-ec2`) that EC2 is allowed to assume (the trust
  policy, `ec2-trust.json`), with a policy that only allows reading and writing *this one bucket*
  (`s3-backup-policy.json`). An **instance profile** attaches it to the server. The AWS CLI on the
  server then gets short-lived credentials automatically, and there's no key on disk to leak.

## Example

On your laptop:

```bash
BUCKET=linkly-course-$(openssl rand -hex 4)
aws s3api create-bucket --bucket "$BUCKET" --create-bucket-configuration LocationConstraint="$AWS_REGION"
aws s3api put-public-access-block --bucket "$BUCKET" \
  --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
aws s3api put-bucket-versioning --bucket "$BUCKET" --versioning-configuration Status=Enabled
aws s3api put-bucket-tagging --bucket "$BUCKET" --tagging 'TagSet=[{Key=Project,Value=linkly-course}]'

aws iam create-role --role-name linkly-course-ec2 \
  --assume-role-policy-document file://app/linkly/aws/ec2-trust.json --tags Key=Project,Value=linkly-course
aws iam put-role-policy --role-name linkly-course-ec2 --policy-name linkly-course-s3-backup \
  --policy-document "$(sed "s/LINKLY_BUCKET/$BUCKET/" app/linkly/aws/s3-backup-policy.json)"
aws iam create-instance-profile --instance-profile-name linkly-course-ec2 --tags Key=Project,Value=linkly-course
aws iam add-role-to-instance-profile --instance-profile-name linkly-course-ec2 --role-name linkly-course-ec2
aws iam wait instance-profile-exists --instance-profile-name linkly-course-ec2
# IAM changes take a few seconds to reach EC2; until then this fails with
# "Invalid IAM Instance Profile name". So: try, wait, try again.
for attempt in 1 2 3 4 5 6; do
  aws ec2 associate-iam-instance-profile --instance-id "$INSTANCE_ID" --iam-instance-profile Name=linkly-course-ec2 && break
  echo "not visible to EC2 yet (attempt $attempt), retrying in 10s..."; sleep 10
done
echo "$BUCKET"                              # you'll need it on the server
```

(us-east-1 is the one region that rejects `--create-bucket-configuration`; leave that option out there.)

On the server (Amazon Linux 2023 has the AWS CLI already), back up the database straight into S3:

```bash
export BUCKET=<the bucket name>
aws sts get-caller-identity                 # the role, not a user: no keys on this machine
set -o pipefail                             # if pg_dump fails, the whole pipeline fails: no empty "backup"
docker compose -f compose.yaml -f compose.ghcr.yaml exec -T postgres pg_dump -U linkly linkly \
  | gzip | aws s3 cp - "s3://$BUCKET/linkly-$(date +%F-%H%M).sql.gz"
aws s3 ls "s3://$BUCKET/"                   # a real dump is kilobytes; ~20 bytes means it was empty
aws s3 ls s3://                             # AccessDenied: the role can only see its own bucket
```

## Check yourself

1. Where do the server's AWS credentials come from, and how long do they last?

<details><summary>Answer</summary>

From the instance metadata service, issued for the instance role through the instance profile.
They're temporary (hours) and rotated automatically; nothing is stored in a file.

</details>

2. What does versioning protect you from?

<details><summary>Answer</summary>

Overwrites and deletions, whether accidental or malicious: older versions stay retrievable. (It
also means deleting a bucket requires deleting every version, which the clean-up script does.)

</details>
